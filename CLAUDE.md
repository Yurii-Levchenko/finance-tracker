# Правила проєкту

Особистий фінансовий трекер на Beancount 3. Для кого він і що має показувати, описано в `PERSONA.md`. Документи проєкту: `PRD.md` (що будуємо), `IMPLEMENTATION_PLAN.md` (кроки), `PROGRESS.md` (що вже зроблено і що далі). Якщо їх ще немає, вони зʼявляться на початку роботи.

Людина, з якою ти працюєш, не має досвіду розробки. Пояснюй коротко і без жаргону: що зроблено, навіщо і як це перевірити.

## Жорсткі правила
- Папка `data/` — лише вхідні виписки. Наявні файли не змінюй, не переноси, не видаляй і не пиши туди результати. Нову виписку можна лише додати як новий файл.
- Після кожної зміни в обліку (`main.beancount`, `transactions.beancount`, `import.py`, `manual.py`, `rules.csv`, `accounts.csv`, `manual.csv`) запускай `uv run bean-check main.beancount`. Зміна не готова, доки перевірка не пройде без жодного повідомлення. Показуй людині результат перевірки.
- «Готово» означає, що перевірка пройшла, а не що код написано.
- Після кожного завершеного кроку онови `PROGRESS.md` і зроби коміт у git з коротким описом українською.
- Дані в цьому репозиторії **лише штучні** (виписки Олі й Марка з умови ДЗ #3), тому `data/` комітимо: репозиторій публічний, і перевіряючий має відтворити облік командою з README. Справжніх виписок сюди не класти ніколи. У git не потрапляють згенеровані `transactions.beancount` і `report.html`, а також ручні `accounts.csv` і `manual.csv`. `rules.csv` комітимо.

## Інструменти
- Python-середовище вже налаштоване через uv (`pyproject.toml`). Усе запускай лише через `uv run …`: `uv run bean-check`, `uv run bean-query`, `uv run fava`, `uv run python …`. Нових пакетів без дозволу людини не встановлюй.
- Лише синтаксис Beancount 3. Збережені запити пишемо нативною директивою `query`, а не `custom "query"`.
- Fava запускаємо на порті 5050 (`-p 5050`): порт 5000 на macOS часто зайнятий AirPlay.
- `app.py` — WSGI-застосунок (стандартний Python, без нових пакетів): локально `uv run python app.py` на 127.0.0.1:5055, на сервері — через `pythonanywhere_wsgi.py`. Вхід за паролем обовʼязковий; паролі (лише PBKDF2-хеші) і ключ підпису сесій — у змінних середовища `TRACKER_USERS`, `TRACKER_SECRET` або у `~/.tracker.env` поза репозиторієм. Ніколи не записуй паролі, хеші чи ключі в код, README чи git.

## Як влаштований облік
- `main.beancount` — опції, відкриття рахунків, збережені запити і рядок `include "transactions.beancount"`. Кожен рахунок, який використовується, має бути відкритий тут директивою `open`.
- `transactions.beancount` генерує `import.py` з усіх CSV у `data/` і правил з `rules.csv`. Формат виписки `import.py` визначає сам: банк Олі (CSV з комами, заголовок `Type,Product,…`) або банк Марка (польський: `Historia operacji`, роздільник `;`, кома в сумах, дати `dd.mm.yyyy`, новіші рядки зверху). Кожна операція отримує тег власника `#olya` або `#marko`. Руками цей файл не правимо: він перезаписується при кожному імпорті.
- Нові категорії — лише через `rules.csv`: додай правило і відкрий рахунок у `main.beancount`, потім перезапусти `import.py`. Ніколи не перекатегоризовуй операції правкою `transactions.beancount`.
- Ручні дані (те, чого немає у виписці) живуть у `accounts.csv` (власні рахунки зі стартовим залишком і джерела доходу) і `manual.csv` (ручні витрати й доходи). Їх правлять форми `app.py` або Excel; `import.py` через `manual.py` дописує їх у кінець `transactions.beancount` з тегом `#manual`. Рахунки з `accounts.csv` відкриваються там же, а не в `main.beancount`. Ручні операції на банківських рахунках (`Assets:Банк:Поточний`, `Assets:Банк:Марко`) заборонені — вони прийшли б двічі. Нових категорій витрат ручні дані не створюють.
- `app.py` після кожного збереження запускає import → перевірку обліку → report.py; якщо перевірка падає, повертає старі CSV.
- Правила категорій живуть лише в `rules.csv` (колонки: шаблон, рахунок, фіксована). Шаблон шукаємо в описі операції без урахування регістру. Перемагає перше правило, що підійшло, тому конкретніші шаблони стоять вище (`Bolt Food` перед `Bolt`). Операція без правила йде в `Expenses:Без-Категорії`. Надходження грошей без правила для доходу йде в `Income:Інше`.
- Рядки у виписці стоять у порядку банку. Колонка залишку (Balance / Saldo po operacji) рахується саме в цьому порядку, навіть коли час операцій усередині дня йде не за зростанням. Не сортуй рядки, коли працюєш із залишком; виписку Марка лише розвертаємо (у ній новіші рядки зверху).
- Якщо в `data/` кілька виписок і рядки повторюються, однаковий рядок (дата завершення, опис, сума, залишок) рахуємо один раз.
- Назви рахунків: корені англійською (`Assets`, `Liabilities`, `Equity`, `Income`, `Expenses`), нижче — українською, слова через дефіс, без апострофів.
- Фіксовані витрати позначаємо тегом `#fixed`, а не окремими рахунками.

## Проєкт
- **Валюта:** лише PLN (`operating_currency "PLN"`). У виписці лише банківський рахунок; готівку чи іншу картку Оля за потреби додає сама через `app.py`.
- **Рахунки:**
  - `Assets:Банк:Поточний` — банківський рахунок Олі; `Assets:Банк:Марко` — рахунок Марка (стартовий залишок 2 860,40 зл на 2026-07-31);
  - `Equity:Початковий-Залишок` — звідки береться стартовий залишок;
  - `Income:Зарплата` (Олі — Product Co sp. z o.o., 9 800 зл/міс; Марка — Northwind Logistics, 7 600 зл/міс), `Income:Інше`;
  - `Expenses:…` — категорії з `rules.csv` плюс `Expenses:Без-Категорії`.
- **Початковий залишок:** 4 500 зл на 2026-07-31, з `Equity:Початковий-Залишок`.
- **Фіксовані** (тег `#fixed`): в Олі — оренда, проїзний ZTM, Netflix, Spotify, Claude.ai, Play (мобільний зв'язок); у Марка — Orange (інтернет і телефон), PGE (світло), Zdrofit (спортзал), YouTube Premium. Усе інше змінне.
- **Власник:** категорії витрат спільні, а чия операція — визначає тег `#olya` / `#marko`. Звіт і перевірка фільтрують за ним.
- **Контрольні цифри змінних витрат** (серпень / вересень): Оля 2 195,21 / 2 582,42, Марко 1 855,57 / 2 432,83. Перевіряє `uv run python check.py`.
- **Нові категорії** (додаються через `rules.csv` на кроці 4 плану): Play → `Expenses:Звязок` (фіксована), Rossmann → `Expenses:Дім-і-Косметика`, Decathlon → `Expenses:Спорт`.
- **Заощадження:** відкладено за місяць = дохід − усі витрати; норма заощаджень = відкладено / дохід. Окремого ощадного рахунку немає.
- **Подушка безпеки:** ціль — 6 × середні витрати повних місяців, до 1 червня 2027 («до літа»). Подушка = гроші на всіх рахунках (`Assets`) на кінець останнього повного місяця (посеред місяця там ще не витрачена зарплата). Прогноз — за середнім «відкладено» повних місяців. Параметри — `CUSHION_MONTHS` і `CUSHION_DEADLINE` у `report.py`, дані — запит «5 Рух по рахунках».
- **Неповний місяць:** жовтень 2026 (дані до 15.10) показуємо з позначкою дати, до якої є дані.
